## 2026-09-20 — 手工同步到 0.1.5-rc.2（未提交）

这次 `--check` 起初挑到 `0.1.6-alpha.2`，改成取 latest 与 next 两个 dist-tag 里较高的那个，落到 `0.1.5-rc.2`。没有走 `--apply`（它遇到第一处失败就整体回滚），而是手动把根、deepbuddy、terminal-probe 三份 manifest 里的 `@deepseek-ai/dsh*` 全部锁到 0.1.5-rc.2，重装后逐道门手工跑。

上游 ui-layout 在这版改了 frame 合同，DeepBuddy 因为禁用了官方 ui-layout 行，必须自己补齐三样东西，全部改在插件自己的层里，没有碰任何官方包：

- 子槽改名。`conversation` 变成 keyed 的 `main`（ui-conversation 以 `conversation` 键注册进去），`details` 变成 `rightbar`（single/root，带 width、viewportWidth、canShow 三个 owner 属性）。adapter.ts 的 FRAME_SLOT_MAP、ThreeColumnFrame 的渲染和测试正则一起改。
- `ctx.layout` 面换成新的五个动词：selectPanel、beginNavigation、toggleSidebar、openRightbar、closeRightbar。layout-store 里新增 panelInfo 快照、rightbar 上报状态和导航 AbortController，去掉了旧的 detailsOpen。
- 新增根级标准钩子 `usePanelInfo`。官方是靠 `ctx.slots.provideRoot({ hooks: { panelInfo } })` 发给每个 slot 组件的，ui-workspace 和 ui-sidebar-right 的组件无条件调用它，所以 DeepBuddy 在挂 `layout` 服务的同一个 effect 里用 store 的快照源提供同名钩子。

右列宽度按官方的求解方式简化：视口减去侧栏再减 400 的中列保底，剩余不到 300 就给 0，否则取 480 与剩余的较小值。列本身常挂载、宽度 0 即关闭，`overflow: visible` 与官方 rightbarCol 一致，占用者全屏时自己盖住 frame。

顺手按用户当场要求去掉了侧栏左上角的像素字标 "DeepBuddy"，品牌只留会话页 hero 一处；fonts.ts 的注释同步改了。

验证结果：deepbuddy 插件 typecheck、build、77 个测试全过；terminal-probe 5 个测试全过；`--smoke` 在 3082 端口起服务 3 PASS / 1 SKIP（SKIP 是没有带 cwd 的会话，与本次改动无关）。没有做过浏览器里的视觉验收，三列真正渲染出来什么样要用户开一下才知道。

备注：官方这版多了 ui-sidebar-right 行（文件、文档预览两个 tab，外加会话头右角的展开按钮），现在它会真的渲染进 DeepBuddy 的 rightbar 列，跟 DeepBuddy 自己的 Inspector dock 并排。要不要在 cordis.patch.yml 里把它禁掉，等视觉验收后再定。

## 2026-09-20 — 打包 app 闪退，五处修复（未提交）

用户装上新打包的 DeepBuddy.app 后闪退。从终端带 `DSH_DESKTOP_SCREENSHOT` 起 app，日志里一道一道撞出来五个问题，全部改在 `apps/desktop` 和 `plugins/deepbuddy` 里，没有碰官方包：

- profile 名被上游保留。0.1.5 的启动器把 `desktop` 这个 profile 名留给官方 Electron 应用，命令行传进来直接拒绝。app 专用 profile 改名 `deepbuddy-app`，落在 `~/.deepbuddy/profiles/deepbuddy-app`。旧的 `profiles/desktop` 目录没有动。
- 插件要在运行时的 node_modules 顶层。cordis-plugin-loader 1.0.3 按裸包名从它自己所在位置往上找 bundle，不再看 profile 目录，所以 stage-runtime.sh 现在把编译好的插件再拷一份到 `dsh-runtime/node_modules/dsh-plugin-deepbuddy`。软链不行，Node 会按真实路径解析。profile 里那份保留，manifest 指的是它。
- schemastery 也要在顶层。插件自己 import 的 `@deepseek-ai/schemastery` 只在 pnpm 隐藏的 `.pnpm/node_modules` 里，stage-runtime.sh 把它加进直接安装列表，和 node-pty、ws 一样拿到顶层软链。
- patchReload 要设成 `startup`。dsh-app-boot 默认 `live`，会加载 HMR 插件去盯 patch 文件，而 HMR 要求 `--expose-internals`，在 Electron 当 node 用的子进程里直接致命。main.js 生成的 profile manifest 明确写 `startup`，与官方 acp/headless/sdk 模板一致。开发路径（scripts/deepbuddy 起 3082）不会撞到这条。
- 客户端服务成环。DeepBuddy 客户端原来把 `uiWorkspace` 列为启动必需，而 0.1.5 的官方 ui-workspace 又等 `layout` 就绪，`layout` 恰是 DeepBuddy 提供的，于是 12 个 entry 全部 pending，页面只剩 HARNESS 的 "Failed to load plugins"。cordis 4 没有可选注入的写法，改成从 inject 里去掉 `uiWorkspace`，adapter 在用户点开新会话、列 home 目录时通过 `ctx.get('uiWorkspace')` 现取，取不到就抛错。这个环开发路径同样存在，之前只做过服务端 smoke 没有开过浏览器，所以没发现。

验证：typecheck、77 个测试全过；重新 `pnpm --filter deepbuddy-desktop run pack`，打包 app 从终端起来截图，侧栏无字标、新建任务是描边卡片、工作区标题紧贴其下、会话列表和输入框都在；开发路径 3082 加 Electron 壳同样渲染出完整会话页。

备注：`scripts/sync-upstream.mjs` 不会更新 stage-runtime.sh 里的 LOCKED_DSH，下次同步要手动改。
